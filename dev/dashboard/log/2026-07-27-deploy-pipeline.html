🔍 이 블록에서 발견한 것

  • 발견·해소
    G3 라이선스 게이트는 Linux CI에서 그대로 두면 실패한다
    네이티브 바이너리는 플랫폼마다 패키지 이름이 다르다. 예외 목록에는 개발 환경(Windows)의 lightningcss-win32-x64-msvc·@img/sharp-win32-x64만 있었는데, npm ci --os=linux --cpu=x64 실측 결과 CI는 lightningcss-linux-x64-{gnu,musl}·@img/sharp-libvips-linux{,musl}-x64를 설치한다 → 허용목록 밖 + 예외 기재 없음 = 실패.
    수정: 4건을 예외 목록에 추가(사유 포함)하고, 게이트가 미설치 예외를 "정리 대상"이라고 부르던 문구를 "다른 플랫폼용 기재"로 분리했다 — 정리 대상이라고 부르면 지우게 되고, 지우면 반대 플랫폼에서 깨진다
  • 발견·해소
    Secrets 확인을 [ -z ... ] && missing=...로 쓰면 정상일 때 실패한다
    GitHub Actions는 bash -e -o pipefail로 실행한다. 값이 있으면 [ -z ]가 거짓 → && 연쇄가 비영 종료 → set -e가 스텝을 죽인다. 즉 Secrets를 제대로 등록한 사람만 배포에 실패하는 정반대 동작. if 블록으로 재작성하고 두 경우를 로컬 bash -e -o pipefail로 실측 확인
  • 기록
    G1(실명 게이트)은 CI에 올릴 수 없다 — 설계 결정으로 못박음
    대조 목록을 CI에서 쓰려면 실명을 Secrets에 올려야 하고, 그것은 게이트가 막으려던 위험(P7 실명 경계)을 게이트 운영이 스스로 늘리는 일이다. 대신 "CI가 G1을 검사하지 않는다"를 워크플로 주석·docs/배포.md §3·제출-게이트 실행 시점 표 세 곳에 명시했다. 실제 통과 시점은 B9 최종 커밋 직전 로컬 npm run gate
  • 기록
    Vercel을 골랐으므로 F13(/t/[state])·F14(next/og)를 계획서 원안대로 유지한다
    GitHub Pages(정적 export)였다면 동적 경로와 동적 OG를 강등해야 했다. next.config.ts는 손대지 않았다
