# 구현 규약 v1.0 — 코드 구조·상태 경계·계약·테스트

> **이 폴더(`impl/`)의 위치**: [features/version1.0/](../../features/version1.0/기능명세_인덱스_v1_0.md)이
> **"무엇이 되어야 하는가"**의 정본이고, 이 폴더가 **"코드로 어떻게 만드는가"**의 정본입니다.
>
> **왜 features 문서를 고치지 않고 새 폴더를 만드는가** — 전역 §7.1의 *작업 중 버전업 금지*
> 원칙 때문입니다. 구현하면서 features 문서를 계속 고치면 (a) 기획서 PDF(동결)와의 대조
> 기준선이 사라지고 (b) 변경노트 누적 체계가 무너집니다. 구현 지식은 이 폴더에 쌓고,
> features 문서는 B8의 v1.1 일괄 버전업에서 한 번에 정리합니다.
>
> 표기 규약(`Pn`·`ADR-n`·`[설계 결정]`·`[추정 설계목표]`)은 기능명세 인덱스와 동일.

## 0. 이 폴더의 문서 작성 규약

**기능 구현 블록에 착수하기 직전에, 그 블록이 다루는 기능의 구현 명세를 먼저 씁니다.**
미리 16개를 다 쓰지 않습니다 — 앞 블록에서 배운 것이 뒤 문서에 반영되어야 하고,
쓰이지 않을 문서에 시간을 쓰지 않기 위해서입니다.

```
impl/version1.0/
├── 구현규약_v1_0.md          ← 이 문서 (전 기능 공통)
├── F01_전술보드_피치_impl.md   ← B4 착수 직전
├── F02_...                    ← B4
├── F05_...                    ← B5 착수 직전
└── ...
```

### 기능별 구현 명세 템플릿 (7섹션)

| # | 섹션 | 내용 |
|---|---|---|
| 1 | 계약 재확인 | 대응 features 문서의 R 항목·GWT를 표로 인용 (누락 방지) |
| 2 | 컴포넌트 트리 | 파일 경로 + Server/Client 표기 + props 타입 |
| 3 | 상태 | 어느 스토어 슬라이스의 무엇을 읽고 쓰는가 |
| 4 | 알고리즘·수식 | 좌표 변환·조정 계층·샘플링 등 구체 산식 |
| 5 | 실패 경로 | features의 IF-THEN 각각에 대응하는 코드 분기 |
| 6 | 테스트 | 단위(순수 함수) · 상호작용 · 실기기 확인 항목 |
| 7 | 근거 태그 회수 | `[추정 설계목표]`를 B8 QA 체크리스트로 이관 |

**섹션 5가 의무인 이유** — features 문서는 기능당 IF-THEN을 3건 이상 갖고 있습니다.
구현에서 이것이 빠지면 "동적 인터랙션이 작동하지 않는 경우 평가 제외"(요강)에 직결됩니다.
정상 경로만 만들고 넘어가는 것을 문서 구조로 막습니다.

## 2. Server / Client 경계

**원칙: 페이지 셸은 Server, 조작 영역만 Client** `[설계 결정]`

| 경계 | 이유 |
|---|---|
| `page.tsx`는 전부 Server Component | JS 실패·차단 시에도 화면이 뜬다 (F08-R5 백지 금지) |
| 기본 확률은 **Server에서 렌더** | `defaults.json.precomputed`를 SSR로 심어 첫 페인트에 확률이 존재 (F08-R1) |
| `'use client'`는 컴포넌트 단위로만 | 피치·슬라이더·예측 패널. 페이지 전체를 Client로 만들지 않는다 |
| Worker 생성은 Client 마운트 후 | SSR 중 `Worker` 참조 금지 |

**"첫 페인트에 확률이 있다"의 구현 의미** — `page.tsx`가 `defaults.json`을 읽어
`ProbabilityBar`에 초기값을 props로 넘깁니다. Client 하이드레이션 후 Worker가 준비되면
같은 값을 재계산해 교체하는데, **값이 같으므로 사용자에게는 아무 일도 일어나지 않습니다.**
이것이 F08의 "빈 화면 금지"를 로딩 스피너 없이 만족시키는 방법입니다.

## 3. 상태 (Zustand 슬라이스)

```typescript
// store/tacticsSlice.ts — 사용자가 만지는 것
interface TacticsSlice {
  formationId: FormationId;
  positions: Position[];          // 길이 11, 정규화 좌표
  sliders: Sliders;               // 4종 0~100
  selectedTokenIndex: number | null;  // F03 클릭-클릭 1단계
  setFormation(id: FormationId): void;
  movePlayer(index: number, pos: Position): void;
  setSlider(key: SliderKey, value: number): void;
  reset(): void;
}

// store/predictionSlice.ts — 엔진이 채우는 것
interface PredictionSlice {
  p: Probabilities | null;        // 단일 추론
  band: WilsonBand | null;
  frames: Frame[];                // MC 스코어 프레임 (HOPs 재료)
  mode: 'fast' | 'precise';
  engine: 'onnx' | 'fallback';    // 폴백 여부 → EstimateBadge
  status: 'idle' | 'loading' | 'inferring' | 'simulating' | 'error';
  progress: { done: number; total: number } | null;
  degraded: boolean;              // F06-R7 자동 강등 → 화면 표기
}

// store/replaySlice.ts — 리플레이 컨텍스트
interface ReplaySlice {
  matchId: MatchId | null;
  interventionMinute: number | null;
  scenario: WinProbPoint[] | null;  // 개입 재계산 결과
}
```

**두 슬라이스를 나누는 이유** — F05-R2("추론 중에는 직전 값을 유지")를 구조로 보장하기
위해서입니다. `tactics`가 변해도 `prediction.p`는 새 결과가 **도착할 때까지 그대로**입니다.
한 슬라이스에 섞으면 "조작했는데 확률이 잠깐 비는" 상태가 코드상 가능해집니다.

**파생값은 스토어에 넣지 않습니다** — `z = (s-50)/50` 같은 값은 `adjust.ts`가 계산합니다.
스토어에 두면 두 곳이 어긋날 수 있습니다.

## 4. Worker 계약 (ML 설계 §6.1 이식 — 임의 변경 금지)

```typescript
// types/worker.ts
type WorkerRequest =
  | { type: 'init' }
  | { type: 'infer';    payload: TacticContext }
  | { type: 'simulate'; payload: TacticContext & { iterations: 5000 | 25000 } }
  | { type: 'replay';   payload: InterventionContext }
  | { type: 'cancel' };

type WorkerResponse =
  | { type: 'ready' }
  | { type: 'result';    payload: { p: [number, number, number]; wilson: Band; frames: Frame[] } }
  | { type: 'progress';  payload: { done: number; total: number } }
  | { type: 'cancelled' }
  | { type: 'error';     payload: { stage: 'load' | 'infer' | 'simulate' } };
```

운영 규칙:

| 규칙 | 값 |
|---|---|
| MC 청크 크기 | **500회** — `progress` 보고 단위이자 `cancel` 반영 지연 상한 |
| `init`→`ready` 사이 조작 | 큐잉 후 **최신 상태 1건만** 추론 (중간 상태 버림) |
| 무응답 타임아웃 | 재기동 **1회** → 그래도 실패면 `fallback.ts` (F05-R6) |
| debounce | 슬라이더·드래그 종료 후 **160ms** `[설계 결정]` — 100ms 프리뷰 예산 이후 |
| 확률 합 | `p` 3원소 합 = 1 ± 1e-6 (assert) |

**`cancel`이 청크 경계에서만 반영되는 것이 왜 괜찮은가** — 500회 계산 시간이 취소 지연의
상한이 됩니다. 5,000회가 1초 목표이므로 청크 1개는 약 100ms이고, 이는 사용자가 "즉시"로
지각하는 범위입니다 (P5).

## 5. 조정 계층 (`lib/tactics/adjust.ts`)

[피처_정의서 §4](../../ml/version1.0/피처_정의서_v1_0.md)의 매핑표를 **순수 함수**로 구현합니다.
Python(학습 시 검증)과 JS(런타임)에 이중 구현되므로 대조 테스트가 의무입니다(ADR-008).

```typescript
interface AdjustInput {
  eloDiff: number;               // 조정 전 Elo 차이
  lambda0: [number, number];     // 기준 λ 쌍 [kor, opp]
  sliders: Sliders;              // 0~100 × 4
  positions: Position[];         // 배치 파생 지표 산출용
  roles: PositionRole[];         // 슬롯 역할 (적합도 페널티)
}
interface AdjustOutput {
  effectiveEloDiff: number;      // Δ_eff — 분류기 입력
  lambda: [number, number];      // 조정 후 λ 쌍 — 스코어 모델 입력
}
export function adjust(input: AdjustInput, k: AdjustConstants): AdjustOutput;
```

구현 순서 (이 순서를 바꾸면 값이 달라집니다):

1. `z = (s - 50) / 50` — 슬라이더 중심화. **기본 상태에서 z=0 → 조정 계층은 항등**
2. 배치 파생 `z_pos_line`(DF 평균 y) · `z_pos_width`(필드 플레이어 x 표준편차) 산출
3. 이중 계상 방지 결합: `z_line = ½·z_slider + ½·z_pos`, `z_width` 동일. 압박·템포는 슬라이더 단독
4. §4.2 매핑표대로 λ 쌍에 이득 항(z 비례)·리스크 항(z² 비례)을 `exp()` 곱셈 적용
5. 포지션 적합도 페널티 — 공격진 이탈은 `λ_kor` 감소, 수비진 이탈은 `λ_opp` 증가
6. **총 조정 상한 정규화**: λ 변화가 기준 대비 ±30%를 넘지 않게 클램프
7. Elo 등가 번역: `Δ_eff = eloDiff + c · 400 · log₁₀((λ_kor/λ_opp) / (λ⁰_kor/λ⁰_opp))`

**1번이 "기본 상태에서 항등"인 것이 중요한 이유** — 첫 화면의 확률이 **순수하게 학습 모델의
출력**이어야 합니다. 기본 상태에 조정이 걸려 있으면 "모델이 뭘 예측했는지"를 아무도 볼 수
없게 됩니다.

**6번 클램프를 빠뜨리면** 슬라이더를 전부 극단으로 올렸을 때 확률이 0/1에 붙어 ADR-008의
양날 설계가 무의미해집니다. 단위 테스트 필수 항목입니다.

## 6. 명명·에러 처리·타입

- 변수·함수 `camelCase` / 컴포넌트·타입 `PascalCase` / 상수 `UPPER_SNAKE_CASE`
- 주석·커밋·문서는 **한국어**. 복잡한 산식에는 반드시 근거 주석 + 문서 링크
- **`any` 금지** (strict). 외부 경계(JSON·postMessage·URL)는 **Zod 파싱으로 좁힙니다** —
  `as` 캐스팅으로 통과시키지 않습니다
- `try-catch`는 단순 로그 금지. 예측 계열 실패는 **반드시 화면 상태로 번역**
  (`engine: 'fallback'` / `status: 'error'`) — 사용자가 보는 것이 비지 않게
- 콘솔 에러 0건이 B8 게이트 (요강 "오류 없이 안정적으로 동작")

## 7. 테스트 전략

| 층 | 도구 | 대상 |
|---|---|---|
| 단위 | Vitest | `adjust.ts`(경계값·클램프·항등) · `wilson.ts` · `encode.ts`(왕복·변조) · `montecarlo.ts`(수렴) |
| 정합 | Vitest + 고정 케이스 | JS `adjust` ↔ B3 Python 참조값 (슬라이더 0/50/100 × 프리셋 4종) |
| ONNX 정합 | Node ORT 하니스 | Python 확률 ↔ ORT 확률, 최대 절대오차 ≤1e-4 (ML-R5) |
| 게이트 | `npm run gate` | 실명·참조 무결성·라이선스 (빌드 차단) |
| 실기기 | 수동 (B8) | U4 10분 시나리오 · 지연 예산 실측 · 폴백 경로 |

**E2E 자동화를 도입하지 않는 이유** `[설계 결정]` — 7일 일정에서 Playwright 시나리오 유지
비용이 실기기 수동 검증보다 크고, 심사는 실기기 기준입니다. 대신 **순수 함수 커버리지를
높게** 유지해 회귀를 단위 테스트가 잡게 합니다.
