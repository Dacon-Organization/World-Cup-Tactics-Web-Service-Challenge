## 1. 계약 재확인

| ID | 요구사항 | 구현 지점 |
|---|---|---|
| F06-R1 | WHEN debounce 종료 → 빠른 모드(5,000회) 자동 실행 | `context` 변경 구독 → `simulate{ iterations: 5000 }`. 강등 시 2,500 |
| F06-R2 | WHEN 정밀 모드 실행 → 진행률 표시 + 취소 버튼 노출 | `progress` 응답 → `ProgressBar` (200ms 지연 마운트, §4.5) |
| F06-R3 | WHEN 완료 → 확률·Wilson 밴드·반복 횟수 함께 표시 | `result{ p, wilson, frames }` + `iterations` 를 `EngineStatusLine`에 문자열로 |
| F06-R4 | IF 취소 → 청크 경계 즉시 중단, 직전 결과 유지 | `cancel` → 취소 플래그 → 다음 청크 경계에서 `cancelled` 응답. 스토어 미변경 |
| F06-R5 | IF 정밀 모드 10초 초과 → 진행률·취소 유지하며 계속, 완료 후 소요 시간 표기 | 중단 로직 없음. `elapsedMs`를 `result`와 함께 표기 |

**GWT** — ① 슬라이더 조작 후 대기 → 자동 실행 + 반복 횟수 표시 ② 정밀 모드 취소 → 1초 내 중단,
직전 결과 유지 ③ 정밀 모드 밴드가 빠른 모드보다 좁다(√5 ≈ 2.24배).

## 3. 상태

전부 [F05 impl §3](F05_온디바이스_예측_패널_impl.md)의 `predictionStore`가 이미 들고 있습니다.
이 문서가 쓰는 것은 `band` · `frames` · `iterations` · `progress` · `degraded` · `status`입니다.

`degraded`만 **세션 동안 되돌리지 않습니다** — B4의 `previewTier`와 같은 원칙입니다. 반복 횟수가
5,000과 2,500 사이를 오가면 밴드 폭이 √2배씩 진동하고, 사용자는 그것을 "전술 때문에 불확실성이
변했다"로 읽습니다. 성능 파생값이 의미 있는 값처럼 보이게 두지 않습니다.

## 4. 알고리즘·수식

### 4.1 스코어 격자 추출 — `blend.ts` 수정

MC 2단계는 집계된 승/무/패가 아니라 **셀 행렬**을 씁니다. 기존 `gridProbabilities`의 i·j 이중
루프를 `scoreGrid()`로 떼어내고, `gridProbabilities`는 그 위에서 합산하게 바꿉니다.

```typescript
/** (gridMax+1)² 미정규화 셀 행렬. cell[i][j] = 자기 i골 · 상대 j골 */
export function scoreGrid(
  lambdaSelf: number, lambdaOpp: number, k: ScoreGridConstants,
): { cells: number[][]; total: number };
```

**부동소수점 결과가 바뀌지 않는 것이 이 리팩터의 수용 조건입니다.** 합산을 같은 i·j 순서로
유지하면 덧셈 순서가 동일해 비트 단위로 같은 값이 나옵니다. B4가 파이썬 참조값과 맞춰 둔
`tests/fixtures/adjust-cases.json` 대조가 깨지면 리팩터가 틀린 것입니다 — 회귀 검사가 이미
자리에 있습니다.

### 4.2 조건부 2단 샘플링 — `montecarlo.ts`

[ML 설계 §4.3](../../ml/version1.0/ML_설계_v1_0.md)의 절차를 그대로 옮깁니다.

**준비 (N과 무관, 1회)**

```
grid = scoreGrid(λ_self, λ_opp, k)
셀을 결과별로 3분할:  win = {(i,j) | i>j},  draw = {i=j},  lose = {i<j}
분할마다 누적합 CDF_r 을 만들고 각 분할의 합으로 정규화
```

**반복 (N회)**

```
① r_k ~ Categorical(p)        ← p 는 F05 §4.5가 낸 표시 확률 (분류기 + 무승부 몫)
② (x_k, y_k) ~ CDF_{r_k}      ← 이진 탐색 1회
   cnt[r_k] += 1
```

**①이 `p`를 쓰고 격자의 주변분포 `p_λ`를 쓰지 않는 것이 이 설계의 핵심입니다.** 전확률 법칙
`P(score) = Σ_r P(r)·P(score|r)`에서 ②는 범주의 주변분포를 건드리지 않으므로, 집계 `p̂`는
`p`로 수렴합니다(평가_설계 §4.2). 화면의 퍼센트(단일 추론)와 배열·밴드(MC)가 어긋날 수 없는
이유가 구현 품질이 아니라 **구조**인 지점입니다.

**분할이 비면** — 격자 상한이 6골이라 어떤 λ에서도 세 분할이 모두 비지 않습니다. 그래도
`CDF_r`의 총합이 0이면 그 범주는 샘플링 불가이므로, `p[r]`을 0으로 재정규화하고 `console.error`를
남깁니다. 조용히 균등 분포로 대체하지 않습니다(구현규약 §6).

### 4.3 난수 — 시드 PRNG `[설계 결정]`

`Math.random()` 대신 mulberry32를 쓰고, 시드를 **컨텍스트에서 유도**합니다.

```
seed = hash32(matchId, round(Δ_eff · 1e6), round(λ_self · 1e6), round(λ_opp · 1e6), iterations)
```

**같은 전술은 항상 같은 밴드를 낳습니다.** 슬라이더를 올렸다 내려 원위치시켰을 때 밴드 폭이
미묘하게 달라지면, 사용자는 그것을 "내 조작 때문"으로 읽습니다. 실제로는 난수 때문입니다.
결정론은 그 오독을 없애고, 단위 테스트의 수렴 검증을 재현 가능하게 만듭니다.

이것이 불확실성을 축소하는 것은 아닙니다 — 밴드 **폭**은 여전히 N이 결정하며(§4.4), 표기되는
반복 횟수도 실제 값입니다.

### 4.4 Wilson 밴드 — `wilson.ts`

[평가_설계 §4.4](../../ml/version1.0/평가_설계_v1_0.md) 산식을 변형 없이 옮깁니다 (z = 1.96).

```
center = ( q + z²/2N ) / ( 1 + z²/N )
half   = z / ( 1 + z²/N ) · √( q(1−q)/N + z²/4N² )
```

**`q`에 `p̂`(MC 집계)가 아니라 `p`(표시 확률)를 넣습니다** `[설계 결정]`. 근거:

- `p`는 입력의 결정론적 함수이므로 **표본 오차가 없는 점추정**입니다. 흔들리는 것은 MC뿐입니다.
- 평가_설계 §4.2가 `p̂ → p`를 증명했으므로, `p`는 `p̂`가 추정하려던 바로 그 값의 가장 좋은 추정치입니다.
- `p̂`를 넣으면 밴드 중심이 표시 퍼센트에서 최대 ~1.4%p 벗어나, **밴드가 표시값을 품지 않는 화면**이
  5% 확률로 나옵니다. F07 수용 기준 "배열·퍼센트·밴드 상호 불일치 0"이 확률적으로만 성립하게 됩니다.
- 밴드의 **폭**은 여전히 N이 지배합니다 — 정밀 모드가 √5배 좁아지는 F06 수용 기준은 그대로입니다.

밴드의 의미는 이렇게 읽힙니다: *"N회 시뮬레이션했을 때 이 결과가 나오는 빈도가 들어갈 범위"*.
모델 자체의 불확실성이 아니라 **시뮬레이션의 표본 오차**이며, 화면 문구도 그렇게 씁니다.

**`p̂`는 버리지 않고 자기 검사에 씁니다** — `|p̂ − p| > 5·SE` 이면 `console.error`. 샘플러가
망가졌을 때(분할 오류·CDF 역전) 조용히 그럴듯한 숫자를 내는 것을 막는 유일한 장치입니다.

**`[0, 1]` 클램프는 장식이 아닙니다** — `q = 1.0`, `N = 5,000`을 산식에 그대로 넣으면 상한이
`1 + ε`(ε ~ 1e-16)로 나옵니다. Wilson이 수학적으로 구간을 벗어나지 않는다는 사실(F07-R4)과
부동소수점 산술이 그것을 지킨다는 것은 별개이며, **실제로 지키지 않는 것을 확인했습니다.**
클램프 없이 F07이 `high`를 퍼센트로 찍으면 `100.0000000000001%`가 화면에 나옵니다.

### 4.5 청크 루프와 취소 — 왜 양보(yield)가 필수인가

```
CHUNK = 500                    // 구현규약 §4 — progress 단위이자 cancel 반영 지연 상한
for (done = 0; done < N; done += CHUNK) {
  <CHUNK회 반복 실행>
  postMessage({ type: 'progress', generation, payload: { done, total: N } })
  await yieldToEventLoop()
  if (cancelRequested) { postMessage({ type: 'cancelled', generation }); return }
}
```

**양보가 없으면 `cancel`은 영원히 도착하지 않습니다.** Worker의 `onmessage`는 큐에 쌓이고,
동기 루프가 도는 동안에는 실행되지 않습니다. 청크로 쪼개기만 하고 이벤트 루프에 제어를
돌려주지 않으면 "청크 경계 취소"는 코드가 아니라 착각입니다.

`SharedArrayBuffer` + `Atomics`로 플래그를 읽는 방법은 **쓰지 않습니다** — COOP/COEP 교차출처
격리가 필요하고, 그것은 F05 §4.2에서 거부한 제약입니다.

```typescript
// setTimeout(0)은 중첩 5회 후 ~4ms로 클램프된다 — 50청크면 200ms를 계산이 아니라 대기로 쓴다
function yieldToEventLoop(): Promise<void> {
  return new Promise((resolve) => {
    const channel = new MessageChannel();
    channel.port1.onmessage = () => resolve();
    channel.port2.postMessage(0);
  });
}
```

### 4.6 Worker의 작업 관리 — 재진입 금지

양보하는 동안 새 `simulate`가 도착할 수 있습니다. `onmessage`가 바로 시뮬레이션을 시작하면
**두 루프가 동시에 돌며 서로의 카운터를 오염시킵니다.**

| 상태 | `simulate` 수신 시 |
|---|---|
| 유휴 | 즉시 실행 |
| 실행 중 | `cancelRequested = true` + **대기열에 저장(최대 1건, 덮어쓰기)**. 현재 청크가 끝나고 `cancelled` 응답 후 대기열 실행 |

메시지 핸들러는 **플래그와 대기열만 만집니다.** 실행은 바깥 루프 하나가 전담합니다.
F06-R6("전술 변경 시 취소 후 최신 재실행")이 이 규칙의 직접 결과입니다.

### 4.7 저성능 자동 강등 (F06-R7)

```
elapsed = (result 수신 시각) − (simulate 전송 시각)      // 메인 스레드 왕복
if (mode === 'fast' && elapsed > 3000) degraded = true   // 이후 5000 → 2500
```

**메인 스레드에서 재는 이유** — 사용자가 겪는 것은 계산 시간이 아니라 왕복 시간입니다. 메인
스레드가 드래그로 바쁘면 `result` 처리가 밀리고, 그 밀림도 체감 지연입니다.

**정직한 예상** — 반복 1회는 균등난수 2개와 이진 탐색 1회뿐이라, 25,000회도 순수 계산은
수 밀리초입니다. 실제 부하는 ORT 단일 추론(1회)과 §4.5의 양보 50회에 있습니다. **이 임계는
현실에서 거의 발동하지 않을 것으로 예상되지만**, 계약이고 저사양 기기의 안전망이므로 구현하고
단위 테스트로 덮습니다(가짜 시계 주입). B8 실측에서 실제 발동 여부를 기록합니다.

강등이 걸리면 화면에 반드시 표기합니다 — `"2,500회 시뮬레이션 · 기기 성능에 맞춰 낮췄습니다"`.
평가_설계 §4.3대로 **넓어진 밴드를 그대로 보여 주고 좁게 보정하지 않습니다.**

### 4.8 HOPs 프레임 추출

N회 표본에서 20개를 **등간격**(`stride = floor(N / 20)`)으로 뽑습니다. 반복이 i.i.d.이므로
어떤 고정 부분집합도 편향 없는 표본이며, 등간격은 그 사실이 코드에서 바로 읽힙니다.
20개는 평가_설계 §4.5의 기본값입니다. 재생은 F07이 담당합니다.

### 4.9 진행률 바 — 200ms 지연 마운트 `[설계 결정]`

F06-R2는 정밀 모드 실행 시 진행률과 취소를 노출하라고 요구합니다. 그런데 §4.7의 이유로
대부분의 실행은 수십 ms에 끝나고, 그때 바를 즉시 그리면 **화면이 한 번 깜빡일 뿐**입니다.
`status`가 `'simulating'`이 된 뒤 200ms가 지나야 마운트합니다. 그 전에 끝나면 아무것도 뜨지
않습니다. 200ms를 넘기는 실행 — 즉 R2가 실제로 보호하려는 상황 — 에서는 정상 노출됩니다.

## 5. 실패 경로

| 계약 | 코드 분기 |
|---|---|
| **F06-R4** 취소 | `cancelRequested` 플래그 → 다음 청크 경계에서 `cancelled` 응답. 메인 스레드는 **스토어를 건드리지 않는다** — `p`·`band`·`frames`가 직전 완료 결과 그대로 남는다. `status`만 `'idle'`로 |
| **F06-R5** 10초 초과 | 중단·강등 로직 **없음**. 진행률과 취소 버튼을 계속 노출하고, 완료 시 `elapsedMs`를 반올림해 `"25,000회 · 12.4초"`로 병기 |
| **F06-R6** 진행 중 전술 변경 | §4.6의 대기열 1건. 취소된 계산의 `progress`·`result`는 봉투 `generation`으로 걸러진다(F05 §5) — 옛 진행률이 새 바를 되감지 않는다 |
| **F06-R7** 저성능 | §4.7. `degraded`는 세션 동안 되돌리지 않으며, 화면 표기 없이 조용히 낮추지 않는다 |
| `p`에 NaN·음수 | `simulate` 진입 시 검증. 위반이면 `error(simulate)` 응답 → 직전 결과 유지 + 콘솔 에러. 샘플링에 넣으면 무한 루프가 된다 |
| CDF 분할 총합 0 | §4.2 — 해당 범주 확률 0으로 재정규화 + 콘솔 에러 |
| `p̂` 이탈 (`>5·SE`) | 콘솔 에러. 결과는 표시하되(밴드는 `p` 기준이라 화면은 정합) 회귀 신호를 남긴다 |
| `iterations`가 유니온 밖 | 타입으로 차단. 런타임 방어로 `simulate` 진입 시 `2500\|5000\|12500\|25000` 확인 후 아니면 5000으로 정정 + 콘솔 에러 |
| 폴백 모드 | **MC는 그대로 돈다.** `p`의 출처가 ONNX냐 §6.3 산식이냐만 다르고, λ는 조정 계층에서 오므로 격자·밴드·프레임이 모두 성립한다 (F06 §8) |
