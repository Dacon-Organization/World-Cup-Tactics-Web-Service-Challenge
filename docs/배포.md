# 배포 — GitHub Actions → Vercel

> **왜 미리 세우는가.** 요강은 "배포 URL이 8/3~8/18 상시 접근 가능"할 것을 요구하고,
> 접근 불가는 **결격**입니다([제출-게이트](제출-게이트.md)). 마감 직전에 배포를 처음
> 시도하는 것이 이 프로젝트에서 가장 값싼 실격 경로입니다. 그래서 기능이 다 끝나기 전에
> 파이프라인부터 세우고, 그 뒤로는 머지할 때마다 자동으로 최신 화면이 올라갑니다.

| 항목 | 값 |
|---|---|
| 배포 대상 | Vercel (프로덕션) |
| 실행 주체 | GitHub Actions — [`.github/workflows/deploy.yml`](../.github/workflows/deploy.yml) |
| 트리거 | `main` 푸시(=PR 머지) 자동 · Actions 탭에서 수동 실행(`workflow_dispatch`) |
| 빌드 위치 | Actions 러너 (Node 24) — `vercel deploy --prebuilt` 로 산출물만 업로드 |
| 배포 URL | *(첫 배포 후 README에 기록)* |

## 1. 최초 1회 셋업 (사용자 직접)

토큰·계정 자격증명 입력은 에이전트가 대신하지 않습니다. 아래 3단계는 사용자가 수행합니다.

### ① Vercel 가입

<https://vercel.com> → **Continue with GitHub** (`mygithub05253`).
Hobby 플랜이면 충분합니다. 카드 등록 불필요.

### ② 프로젝트 생성 + 3개 값 확보

레포 루트에서:

```bash
npx vercel link
```

대화형으로 프로젝트를 만들면 `.vercel/project.json`이 생기고 그 안에 `orgId`·`projectId`가
들어 있습니다. 이 파일은 이미 `.gitignore` 대상이라 커밋되지 않습니다.

토큰은 <https://vercel.com/account/tokens> → **Create Token** (Scope: 계정 전체, 만료: 대회
종료 이후로 넉넉히).

### ③ GitHub Secrets 3종 등록

레포 **Settings → Secrets and variables → Actions → New repository secret**:

| 이름 | 값 |
|---|---|
| `VERCEL_TOKEN` | ②에서 발급한 토큰 |
| `VERCEL_ORG_ID` | `.vercel/project.json`의 `orgId` |
| `VERCEL_PROJECT_ID` | `.vercel/project.json`의 `projectId` |

셋 중 하나라도 없으면 `deploy` 워크플로는 **첫 단계에서 사람이 읽을 수 있는 오류로 실패**합니다.
조용히 건너뛰고 초록불을 보여 주지 않습니다.

> `ci` 워크플로는 Secrets와 무관하게 지금 바로 동작합니다. Vercel 셋업 전에도 PR 검증은 돕니다.

## 2. 워크플로 2종

### `ci.yml` — 검증

`pull_request` + `push: main`. 브랜치별 `concurrency`로 연속 푸시 시 이전 실행을 취소합니다.

| 단계 | 명령 | 막는 것 |
|---|---|---|
| 타입 | `npm run typecheck` | strict 위반·`any` 누수 |
| 린트 | `npm run lint` | ESLint·a11y 규칙 위반 |
| 테스트 | `npm test` | 조정 계층·스토어 회귀 |
| G2 | `npm run gate:refs` | 데이터 스키마·참조 무결성 깨짐 |
| G3 | `npm run gate:license` | 허용목록 밖 라이선스 유입 |
| 빌드 | `npm run build` | 프로덕션 빌드 실패 |

### `deploy.yml` — 배포

`push: main` + 수동. `deploy-production` 단일 concurrency 그룹이라 연속 머지 때 옛 배포가
새 배포를 덮어쓰지 않습니다.

Secrets 확인 → 설치 → G2·G3·테스트 → `vercel pull` → `vercel build --prod` →
`vercel deploy --prebuilt --prod` → 배포 URL을 **Actions 실행 요약(Step Summary)** 에 기록.

## 3. CI가 검사하지 않는 것 — G1(실명 게이트)

| 게이트 | CI | 이유 |
|---|:---:|---|
| G1 `gate:names` | ❌ | 대조 목록 `data/gate/real-names.txt`가 **실명을 담아 커밋 금지**. `/data/`는 `.gitignore` 대상이고, 게이트는 목록이 없으면 통과가 아니라 **실패**하도록 설계돼 있습니다([`scripts/gates/names.ts`](../scripts/gates/names.ts)) |
| G2 `gate:refs` | ✅ | 입력이 전부 커밋된 파일 |
| G3 `gate:license` | ✅ | 입력이 `node_modules` + 커밋된 예외 목록 |

실명 목록을 GitHub Secrets에 넣으면 CI에서 G1을 돌릴 수는 있습니다. 하지만 그것은 **실명
유출 경로를 하나 더 만드는 일**이고, 게이트가 막으려던 위험(P7 실명 경계)을 게이트 운영이
스스로 늘리는 셈이라 하지 않습니다.

→ **G1은 로컬 전용 수동 게이트**입니다. 실제 통과 시점은 B9 최종 커밋 직전의 로컬
`npm run gate` 전량 실행입니다.

```bash
npm run gate
```

### 플랫폼별 네이티브 바이너리 (G3 관련)

개발은 Windows, CI·배포 빌드는 Linux라 sharp·lightningcss의 네이티브 패키지 **이름이 다릅니다**.
`scripts/gates/license-exceptions.json`에 양쪽을 모두 기재해 두었습니다. 지금 플랫폼에 없는
쪽은 게이트가 `다른 플랫폼용 기재 (이 환경에는 미설치)` 참고 줄로만 표시합니다 — **지우면
반대 플랫폼에서 게이트가 깨집니다.**

## 4. 문제 해결

| 증상 | 원인 · 대처 |
|---|---|
| `GitHub Secrets 누락: ...` | §1③ 미완료. 이름 철자까지 정확히 일치해야 합니다 |
| `Error: No existing credentials found` | `VERCEL_TOKEN`이 만료·폐기됨 → 재발급 후 Secret 갱신 |
| `Project not found` | `VERCEL_PROJECT_ID`가 다른 프로젝트를 가리킴. `.vercel/project.json` 재확인 |
| `vercel build` 실패인데 로컬은 성공 | 대소문자 구분 — Windows는 `Pitch.tsx`/`pitch.tsx`를 같게 보고 Linux는 다르게 봅니다. import 경로 철자 확인 |
| G3만 CI에서 실패 | 새 의존성의 Linux 네이티브 변종이 예외 목록에 없음 → 실패 로그의 패키지 이름을 예외 목록에 추가 |
| 배포는 성공인데 화면이 옛날 것 | 브라우저 캐시 또는 Service Worker(F05에서 도입 예정). 시크릿 창으로 재확인 |

## 5. 확인 체크리스트 (배포 후)

- [ ] Step Summary의 URL이 200으로 열린다
- [ ] **시크릿 창**에서 로그인·가입 없이 열린다 (요강: 별도 키 없이 확인 가능)
- [ ] **모바일 회선**(Wi-Fi 끄고 LTE)에서 열린다 — 심사자가 모바일로 열 가능성이 전제
- [ ] 첫 페인트에 피치·토큰·확률이 이미 있다 (F08-R1 · SSR 기본 상태)
- [ ] 개발자도구 네트워크 탭에 **외부 도메인 요청 0건** (C1 온디바이스 주장)
