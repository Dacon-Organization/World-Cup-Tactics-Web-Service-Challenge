# P19 — Pointer Events 커스텀 드래그 구현 근거·모바일 함정·WCAG 2.5.7 정합

- **발주일**: 2026-07-27 (B4 착수 직전 적재) / **수행일**: 2026-07-27
- **회수일**: 2026-07-27
- **트리거**: T4 (기술 미검증) — P5 파생
- **블로킹 대상**: **F02**(드래그앤드롭) 구현 · F03(클릭-클릭·키보드 대안)의 필수성 판정 ·
  F02 잔여 `[설계 결정: long-press 지연 도입 여부]`
- **조사 방식**: 에이전트 자체 리서치 — MDN 1차 문서 4종(Pointer Events API ·
  `touch-action` · `setPointerCapture` · `-webkit-touch-callout`) + W3C WAI
  Understanding WCAG 2.2 원문 직접 대조.

---

## 왜 이 건이 필요했는가

P5(NN/g)는 F02의 **UX 스펙**(고스타·드롭섀도·스냅 마그네티즘·손가락 오프셋)을 완결
수준으로 확정했지만, **구현 API 수준의 근거는 전무**했습니다. `docs/research/findings/`
전수 검색 결과 `Pointer Event`·`touch-action`·`setPointerCapture` 언급이 P4·P5 원문의
스치는 수준을 넘지 않았습니다.

이 공백이 위험한 이유는 요강 조항에 직결되기 때문입니다 — **"동적 인터랙션이 실제로
작동하지 않으면 해당 기능 평가 제외"**. 모바일 터치 드래그는 데스크톱에서 완벽해 보여도
iOS Safari에서 브라우저 팬 제스처에 가로채이면 **아무것도 안 움직이는 화면**이 됩니다.
심사자가 모바일로 열 가능성을 전제하는 프로젝트 규약과 정면으로 충돌합니다.

## 조사 질문 (프롬프트 대체)

1. Pointer Events로 커스텀 드래그를 만들 때 반드시 지켜야 하는 API 계약은 무엇인가?
2. `touch-action`을 어디에 어떻게 걸어야 하는가 — 걸지 않으면 무슨 일이 생기는가?
3. iOS Safari의 롱프레스 콜아웃·텍스트 선택을 표준 방법으로 억제할 수 있는가?
   (F02의 열린 `[설계 결정: long-press 지연]`의 답)
4. WCAG 2.5.7은 몇 등급이고, 우리 전술보드가 그 적용 대상인가?

## 요약 및 판단

### Q1. 드래그 구현의 API 계약 — 4가지가 강제된다

MDN *Pointer events* 문서가 제시하는 표준 패턴은 다음과 같습니다:

```
pointerdown  → el.setPointerCapture(ev.pointerId)
pointermove  → 좌표 추적 (스토어 커밋 금지 — F02 [설계 결정])
pointerup    → 커밋 + 캡처 자동 해제
pointercancel→ 원위치 복귀 + releasePointerCapture()
```

| # | 계약 | 1차 출처 원문 근거 | 우리 코드에서의 의미 |
|---|---|---|---|
| C1 | **캡처는 DOM 이동 *후에*** | "If you need to move an element in the DOM, then make sure to call `setPointerCapture()` **after DOM movements**" (MDN Pointer events) | 토큰을 드래그 중 최상위 레이어로 재부착하는 설계라면 **재부착 뒤에** 캡처. 순서가 뒤집히면 캡처가 조용히 풀려 손가락을 따라오지 않는다 |
| C2 | **`NotFoundError` 방어** | `setPointerCapture()`는 "`pointerId`가 활성 포인터와 매칭되지 않으면" `NotFoundError` DOMException을 던진다 (MDN setPointerCapture) | 이벤트 처리 지연·재렌더 사이에 포인터가 사라질 수 있다. `try/catch`로 감싸고 실패 시 드래그를 시작하지 않는다 |
| C3 | **캡처 중 enter/leave 계열이 죽는다** | 캡처가 걸리면 "`pointerover`, `pointerenter`, `pointerleave`, `pointerout`은 **발화하지 않는다**" | 드롭존 하이라이트를 `pointerenter`로 만들면 **동작하지 않는다.** 좌표 계산으로 근접 판정해야 한다 (스냅 마그네티즘도 어차피 좌표 기반) |
| C4 | **`isPrimary`로 멀티터치 차단** | 터치의 primary는 "다른 활성 터치가 없을 때 화면에 닿은" 포인터 | **F02-R7("두 번째 손가락 무시")의 실제 구현 지점.** `if (!ev.isPrimary) return;` 한 줄, 또는 활성 `pointerId` 1개만 추적 |

**호환성 마우스 이벤트 주의** — MDN: 포인터 이벤트를 지원하는 브라우저도 하위 호환을 위해
마우스 이벤트를 **함께** 발화합니다. 포인터 핸들러와 마우스 핸들러를 동시에 달면 같은
조작이 두 번 처리됩니다. **포인터 계열만 사용**합니다(우리는 IE 지원 대상이 아니므로 가능).

### Q2. `touch-action` — 이 프로젝트에서 가장 위험한 한 줄

**걸지 않으면**: MDN `touch-action` 원문 — "기본적으로 패닝(스크롤)과 핀치 제스처는
브라우저가 **전적으로** 처리한다. Pointer events를 쓰는 애플리케이션은 **브라우저가 터치
제스처를 처리하기 시작하면 `pointercancel` 이벤트를 받는다**." → 손가락으로 토큰을 끌면
브라우저가 "스크롤 의도"로 판정해 우리 드래그를 **취소**시킵니다. F02가 통째로 죽습니다.

**그런데 `none`을 함부로 걸면 접근성이 죽는다** — MDN이 명시적 경고를 답니다:

> "`touch-action: none;` 선언은 브라우저의 확대 기능을 저해할 수 있다. 이는 저시력
> 사용자가 페이지 내용을 읽고 이해하지 못하게 만든다." (참조: WCAG 1.4.4 Resize text)

**⚠️ 채택 결정 `[설계 결정]`**: `touch-action: none`은 **선수 토큰 요소에만** 선언하고
피치 컨테이너·페이지에는 절대 걸지 않습니다. 그러면 토큰 위 제스처만 우리가 가져가고,
피치 여백·페이지 전체의 확대·스크롤은 살아 있습니다. 접근성이 명시 범위인 프로젝트에서
"드래그를 살리려다 확대를 죽이는" 교환은 허용되지 않습니다.

**⚠️ 정적 선언 강제**: MDN — 애플리케이션은 "**어떤 이벤트 리스너가 호출되기도 전에**
브라우저가 의도를 알 수 있도록 `touch-action`을 써야 한다"며, "**제스처가 시작된 뒤의
`touch-action` 변경은 현재 제스처의 동작에 아무 영향이 없다**"고 못박습니다.
→ **드래그 시작 시 JS로 `touch-action`을 바꾸는 설계는 작동하지 않습니다.** CSS에
정적으로 선언되어 있어야 합니다.

### Q3. iOS 롱프레스 — F02 잔여 `[설계 결정]`의 답: **long-press 지연을 도입하지 않는다**

- `-webkit-touch-callout: none`은 iOS 롱프레스 콜아웃(컨텍스트 메뉴)을 끄지만,
  MDN이 **비표준**으로 분류하고 "프로덕션 사용을 권장하지 않는다 — 브라우저 지원이
  제한적이고 변경·제거될 수 있다"고 명시합니다. Apple Safari CSS Reference에만 문서화된
  Apple 전용 속성입니다.
- 따라서 **의존하지 않습니다.** 콜아웃·선택 억제의 1차 수단은 이미 확보돼 있습니다:
  토큰 한정 `touch-action: none`(브라우저 제스처 차단) + 표준 `user-select: none`(텍스트
  선택 차단). `-webkit-touch-callout: none`은 **있으면 좋은 보강**으로만 넣고, 없어도
  기능이 성립해야 합니다.
- **long-press 지연 미도입 근거**: F02 §6의 걱정("스크롤하려다 토큰이 끌려오면?")은
  `touch-action`을 **토큰에만** 거는 것으로 이미 해소됩니다 — 토큰 밖은 브라우저가
  정상 스크롤하고, 토큰 위는 우리가 즉시 가져갑니다. 여기에 long-press 지연을 더하면
  P5가 확정한 "즉각 반응"(~100ms)을 스스로 깨고, WCAG 2.5.7 대안 경로와도 무관하게
  조작 비용만 올립니다. **실기기 확인은 B8에서 하되, 기본 설계는 지연 없음으로 확정.**

### Q4. WCAG 2.5.7 — **AA 등급**이고, 우리가 정확히 그 예시다

W3C WAI *Understanding SC 2.5.7 Dragging Movements* 원문:

> "All functionality that uses a dragging movement for operation can be achieved by a
> single pointer without dragging, unless dragging is essential or the functionality is
> determined by the user agent and not modified by the author."

- **등급: AA** · **도입: WCAG 2.2** (2.1에는 없던 신규 기준)
- "single pointer" = "화면의 한 점만 지목하는 입력 방식 — 마우스, 터치스크린의 손가락
  하나, 스타일러스"
- **Understanding 문서가 우리 화면을 그대로 예시로 든다**:
  - "칸반 위젯…사용자가 요소를 드래그해 다른 열로 옮길 수 있다. **한 번의 탭이나 클릭으로
    요소를 선택한 뒤 화살표 버튼을 활성화**해서도 같은 일을 할 수 있다"
  - "태스크 보드…열 사이로 항목을 드래그 앤 드롭…**선택된 요소를 다른 열로 옮기는 팝업
    메뉴를 추가로 제공**한다"

**판정**: 전술보드의 선수 배치는 "드래그가 본질적(essential)"인 기능이 **아닙니다**.
좌표 이동은 클릭-클릭이나 방향키로 동일한 결과를 낼 수 있기 때문입니다(F03이 이미
그렇게 설계돼 있습니다). 따라서 **F03은 "있으면 좋은 접근성 보너스"가 아니라 AA 준수의
필수 조건**이며, F02 단독 구현은 기준 미달입니다 — F02 §8이 적어 둔 "본 기능 단독으로는
접근성 요건 미충족"이 1차 출처로 확증됐습니다.

**B4 범위 판정**: F03을 F02 뒤로 미루면 그 사이 어떤 배포도 AA 미달 상태입니다.
계획서가 F02·F03을 같은 블록(B4)에 둔 것은 우연이 아니며, **강등 트리거가 걸려도 F03은
F02와 함께 살아남아야 합니다**(계획서 "P0 수용 기준 불가침"과 정합).

## 구현 체크리스트 (B4가 그대로 소비)

```css
/* 토큰에만. 피치·페이지에 걸면 확대가 죽는다 (WCAG 1.4.4) */
.player-token {
  touch-action: none;      /* 필수 · 정적 선언 (제스처 시작 후 변경은 무효) */
  user-select: none;       /* 표준 */
  -webkit-user-select: none;
  -webkit-touch-callout: none; /* 비표준 — 보강일 뿐, 의존 금지 */
  cursor: grab;
}
```

- [ ] `pointerdown`에서 `isPrimary` 아니면 즉시 반환 (F02-R7)
- [ ] DOM 재부착이 있다면 **그 후에** `setPointerCapture` (C1)
- [ ] `setPointerCapture`를 `try/catch`로 감싸기 — `NotFoundError` (C2)
- [ ] 드롭존 하이라이트를 `pointerenter`로 만들지 말 것 — 캡처 중 발화 안 함 (C3)
- [ ] `pointercancel` 핸들러 = F02-R6(회전·전화 수신)의 구현체. 원위치 복귀 + 캡처 해제
- [ ] `pointermove`에서 스토어 커밋 금지 — 로컬 상태만 (F02 `[설계 결정]`)
- [ ] 마우스 이벤트 핸들러 병용 금지 — 호환성 이벤트로 이중 처리됨
- [ ] F03(클릭-클릭 + 키보드)을 **F02와 같은 블록에서** 완료 — WCAG 2.5.7 AA 필수 (Q4)

## 미확인으로 남긴 것 `[미확인 유지]`

- iOS Safari 실기기에서의 실제 `pointercancel` 발화 타이밍(전화 수신·앱 전환·회전)은
  문서화 수준이 낮습니다 → **B8 실기기 QA에서 F02-R6 시나리오로 직접 확인**합니다.
- SVG 좌표 변환(`getBoundingClientRect` ↔ `viewBox`)은 표준 동작이라 별도 조사를 하지
  않았으나, `preserveAspectRatio` 레터박싱이 생기면 비율이 어긋납니다 → 피치 SVG는
  컨테이너와 종횡비를 일치시켜 레터박스가 생기지 않게 합니다 `[설계 결정]`.
